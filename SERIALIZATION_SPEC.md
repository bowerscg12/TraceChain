# TraceChain Serialization & Hashing Specification (v1)

Owner: Caleb Bowers (API / database). Consumers: Nick Crockett (contract), Nick Frank (frontend / QR).

This document is the **single shared contract** for how item details are turned into the `detailsHash`
that is stored on-chain. Every component that computes the hash (the TraceChain API in Node, the consumer's
browser, any future mobile client) must implement **exactly** this spec, independently, and must produce
byte-identical output for the same record. Team risk D6 Risk 7 says that any difference between the API
and the browser will make a genuine pair show "Not verified" and look like fraud. This spec plus the hash
equality tests in this spike are the mitigation.

## 1. Hashed fields, in this exact order

| # | Field | Example |
|---|-------|---------|
| 1 | `itemId` | `TC-2026-000123` |
| 2 | `brand` | `Nike` |
| 3 | `styleCode` | `DD1391-100` |
| 4 | `colorway` | `White/Black` |
| 5 | `size` | `10.5` |
| 6 | `manufacturer` | `Pou Chen Corp.` |
| 7 | `countryOfManufacture` | `Vietnam` |
| 8 | `productionBatch` | `PB-2026-07-A` |
| 9 | `productionDate` | `2026-07-14` |
| 10 | `registeredBy` | `0x70997970c51812dc3a010c7d01b50e0d17dc79c8` |

**Excluded from the hash:** `status` (changes from `pending` to `confirmed` after the on-chain transaction) and
`createdAt` (a database timestamp that is never shown to the consumer). If either were hashed, the hash would
change for reasons that have nothing to do with the provenance record, and a genuine item would fail.

**Why a fixed order and not an object?** `JSON.stringify` of an object depends on key insertion order, which
differs between languages, ORMs and database drivers. A positional array removes that degree of freedom.

## 2. Normalization (done ONCE, by the API, at write time)

Normalization happens **before** the record is stored and before it is hashed. The database therefore holds
the already-normalized values. Readers (the browser) must **not** re-normalize beyond what is listed under
"Reader rules" below; they hash what they are given. This keeps the two implementations symmetric: the
browser is checking "is the stored record still the one that was hashed?", not "would this record normalize
to the same thing?".

| Rule | Detail | Why |
|------|--------|-----|
| All values are strings | Every one of the 10 values is a JS/JSON string. Numbers, booleans and null are rejected at the API. | `JSON.stringify(10.5)` and `JSON.stringify("10.5")` differ by two quote characters, which changes the hash. |
| Trim | Leading and trailing whitespace removed (`String.prototype.trim()`). Internal whitespace is kept. | Form fields and spreadsheets routinely add stray spaces; a producer typing `"Nike "` means `"Nike"`. |
| Case preserved | Letter case is **not** changed for any field except `registeredBy`. | Style codes and colorways are case-significant product data (`"Bred"` vs `"BRED"` are different records and should be). |
| Unicode NFC | Every string is normalized with `String.prototype.normalize('NFC')`. | `é` can be one code point (U+00E9) or two (`e` + U+0301). They look identical and compare equal to a human but are different bytes, so they hash differently. NFC picks one canonical form. |
| `productionDate` | Must match `^\d{4}-\d{2}-\d{2}$` **and** be a real calendar date (so `2026-02-30` and `2025-02-29` are rejected, `2024-02-29` accepted). Timestamps, `MM/DD/YYYY`, etc. are rejected. Stored and hashed as that 10-character string. | Dates are the biggest drift risk. See §5 for the PostgreSQL DATE trap. |
| `registeredBy` | Must be `0x` followed by exactly 40 hex characters. Lowercased before storing and hashing. Taken from the authenticated producer (`X-Producer-Address` header), never from the request body. | Ethereum addresses are case-insensitive; EIP-55 checksum casing varies between wallets and libraries. Lowercasing makes `0xAbC…` and `0xabc…` the same producer. |
| `size` | Stays a string exactly as entered after trim and NFC (`"10.5"` stays `"10.5"`, `"09"` stays `"09"`). | Sizes are labels, not quantities. `09` → `9` or `10.5` → `10.50` would silently change the hash. |
| `itemId` | Generated by the API as `TC-{year}-{6-digit zero-padded sequence}` from a PostgreSQL sequence, e.g. `TC-2026-000123`. | Guarantees uniqueness (FR-01) and is short enough for `bytes32` on-chain. |
| Required | All 10 values must be non-empty **after** trimming. | An empty field is an incomplete origin record (FR-02). |

### Reader rules (browser / any verifier)
A reader takes the 10 values exactly as returned by `GET /items/:itemId`, confirms each is a string, and hashes
them. The reader does **not** trim, lowercase or NFC-normalize them. If a stored value had been altered to
include a trailing space, the reader must detect that as a change. (Whitespace-only edits made *through the
API* never reach storage, because the API trims; whitespace edits made *directly in the database* are a
tamper and are detected.)

## 3. Serialization

```
serialized = JSON.stringify([itemId, brand, styleCode, colorway, size, manufacturer,
                             countryOfManufacture, productionBatch, productionDate, registeredBy])
bytes      = UTF-8 encoding of serialized
```

* `JSON.stringify` with **no** replacer and **no** indent argument: no extra whitespace anywhere.
* JSON escaping is part of the spec: `"` becomes `\"`, `\` becomes `\\`, control characters become `\uXXXX`
  or short escapes (`\n`), per ECMA-404 / RFC 8259. Characters outside ASCII (accents, emoji) are **not**
  escaped by `JSON.stringify`; they are emitted as-is and then UTF-8 encoded. Implementations in other
  languages must match this exactly (for example, Python's `json.dumps` must be called with
  `ensure_ascii=False, separators=(',', ':')`).
* Lone surrogates are not expected in real data; `JSON.stringify` emits them as `\udXXX` escapes (well-formed
  JSON.stringify, ES2019). Our API rejects malformed UTF-16 input to avoid this case entirely.

Example (record `TC-2026-000001`):

```
["TC-2026-000001","Nike","DD1391-100","White/Black","10.5","Pou Chen Corp.","Vietnam","PB-2026-07-A","2026-07-14","0x70997970c51812dc3a010c7d01b50e0d17dc79c8"]
```

## 4. Hash

```
detailsHash = "0x" + lowercase_hex( SHA-256( bytes ) )     // 66 characters total
```

* SHA-256 gives exactly 32 bytes, so `detailsHash` fits a Solidity `bytes32` directly (no truncation, no keccak).
* Hex is lowercase. Comparisons should still be done case-insensitively on the hex part to be robust against
  libraries that return checksummed/uppercase hex, but every producer of a hash must emit lowercase.
* Known test vector (verify your implementation against this before anything else):

  | Input array | SHA-256 |
  |-------------|---------|
  | `["TC-2026-000001","Nike","DD1391-100","White/Black","10.5","Pou Chen Corp.","Vietnam","PB-2026-07-A","2026-07-14","0x70997970c51812dc3a010c7d01b50e0d17dc79c8"]` | `0x5b8277b17b53b2915e4c84ca8796b85388f81c8ea11636fb6c0d48ae522fb573` (pinned in `src/hash.vector.json`, checked by both implementations) |

## 5. On-chain encoding

* `itemIdBytes32 = ethers.encodeBytes32String(itemId)`: the UTF-8 bytes of the itemId right-padded with zero
  bytes to 32 bytes. `encodeBytes32String` allows at most 31 bytes; our format is 14 characters.
  The reverse is `ethers.decodeBytes32String`.
* `detailsHash` is passed to the contract as `bytes32` exactly as the `0x…` 64-hex string.
* Only `itemIdBytes32` and `detailsHash` (plus `msg.sender` and block timestamp, which the chain records
  anyway) go on-chain. No names, no addresses of people, no product details (NFR-04 / NFR-05).

## 6. The PostgreSQL DATE trap (why `productionDate` is handled specially)

`production_date` is a `DATE` column. By default the `pg` Node driver converts `DATE` values into JavaScript
`Date` objects at **local midnight** of the process's timezone (e.g. `2026-07-14` → `Date(2026-07-14T00:00 local)`).
When that `Date` is later turned back into a string with `toISOString()` (which is UTC), any process running
west of UTC (America/New_York) gets `2026-07-13T04:00:00.000Z` and the day **shifts backwards by one**.
Processes east of UTC are fine for `toISOString()` but break the other way if someone uses `toLocaleDateString`.
The hash would then differ depending on which machine, in which timezone, served the request. That is exactly
the "genuine item looks like fraud" failure in Risk 7.

**Fix (mandatory for every `pg` client in TraceChain):** register a type parser override for the `DATE` type
(OID `1082`) that returns the raw text the server sends, unchanged:

```js
const { types } = require('pg');
types.setTypeParser(1082, (value) => value);   // DATE  -> 'YYYY-MM-DD' string, no Date object, no timezone math
```

With this override, `SELECT production_date` returns the string `'2026-07-14'` in every timezone. The spike's
Test 1 runs the API under `TZ=UTC`, `TZ=America/New_York` and `TZ=Asia/Tokyo` with the browser timezone set to
match, to prove that the stored date round-trips byte-for-byte.

The same reasoning is why `createdAt` (a `timestamptz`) is excluded from the hash: it is intrinsically
timezone-dependent and is not part of the provenance record.

## 7. Two independent implementations (required)

1. **API (Node):** `src/hash.js` — `crypto.createHash('sha256')`, `Buffer.from(str, 'utf8')`.
2. **Browser:** `public/verify-hash.js` — `new TextEncoder().encode(str)` and `crypto.subtle.digest('SHA-256', bytes)`.

The browser file must be written from this document, not copied from or importing `src/hash.js`. If both
agree on the 100-record test dataset (including the 20 edge cases) across three timezones, we have evidence
that the spec is unambiguous enough for Nick Frank's frontend and any future client to implement.

## 8. Versioning

This is spec **v1**. Any change to the field list, order, normalization or algorithm changes the hash of every
existing record, so a change requires a new version number and the on-chain record would need to carry the
version. Do not change v1 after records are registered against it.
